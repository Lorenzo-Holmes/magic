# 我欲飞升 V3：按《一念逍遥》窗口结构重建视觉

日期：2026-09-10。状态：设计与工程规划，未实施新的生产 UI，未通过用户视觉验收。

基线：v2.2.1，提交 `306bf79d438e996f547b31d93032e55e86b49827`。本轮开始时工作区干净。

## 1. 本次目标与边界

用户要的是接近《一念逍遥》的游戏画面、页面组织和控件质感，不是“加一张水墨图”“把所有按钮改成圆形”或继续堆叠 CSS。

执行方向：依据已解析的 Prefab 层级、RectTransform、图集分类和窗口分工，重新实现适配现有 Web 游戏的窗口系统；保留自己的规则、存档和内容。参考结构，不把不可读的 Lua 冒称为已经恢复的源代码，不把商业 APK 或其资源打进公开仓库。

本规划的 `WindowController`、`ViewBinder` 等名称属于拟建 Web 实现，不是声称原游戏存在这些同名类。图中画面是设计目标；未生成、未验收的美术不能标成已交付。

不迁移到 Unity，不引入 WebGL 引擎，不增加联网、付费、宗门战、药园种植、自动挂机收益等新玩法。参考中存在的功能，不等于本项目已具备。

## 3. 视觉方向

### 3.1 风格基准

核心目标：灰白水墨山川、细墨线建筑、适度工笔的人物与器物、少量朱印、清晰的信息面板。不是深褐古纸海报，不是深绿色仪表盘，不是靠大光圈制造仙侠感。

场景层有疏密与远近；交互层有真实底板和图标；文字层保持规整。画面可以有彩色法术，但不应把整屏染成金黄或青绿。

以下色值是本项目候选设计 token，未声称从原作精确取色：

| Token | 候选值 | 用途 |
|---|---|---|
| paper | #ECECE6 | 面板主体 |
| paper-highlight | #F6F5EE | 局部提亮 |
| ink | #292E2C | 主要文字和墨线 |
| secondary-ink | #626A64 | 次要文字 |
| mineral-grey | #8C9694 | 山石/界面分隔 |
| mineral-blue | #748A8C | 建筑与少量灵气 |
| aged-gold | #AA9465 | 细框/稀有状态 |
| cinnabar | #9A473D | 选择印记/需要处理的状态 |

字体分工：页名与短题签用宋体/楷意层级；正文、按钮说明和数值用清晰系统字体。首版不引入或分发原作字体。移动端正文以 14–16 CSS px、次要信息 12–13 px 为目标，不能通过缩到 6–9 px 来塞下布局。稀有度同时使用文字和边框，不只靠颜色。

### 3.2 三类页面，不能混用

1. 场景导航：洞府、山海。主要阅读对象是建筑与地点。
2. 主体展示：人物、炼器。主要阅读对象是道身或器炉，旁边是槽位与参数。
3. 信息管理：行囊、属性、日志、设置。主要阅读对象是物品与文字，应该使用列表、页签和面板。

原作 `BaggageWnd` 本来就有 ScrollView、Viewport、ItemIcon_new 和 sell_panel。把行囊做成三个漂浮菜单不是对参考的复现。

## 4. 页面蓝图

### 4.1 洞府：HouseWnd → CaveWindow

构图：上部远山和云气，中部主殿与修炼石台，下部丹炉、藏物处、山门小径；建筑采用疏密不一的竖向布局。不能先生成一张任意山水再把按钮塞入空位。

场景图层：远山底景 → 山体/主殿 → 修炼角色 → 建筑/物件 → 云气与枝叶前景。HUD 不进入透视、不随背景视差移动。

可用热点仅对应已有功能：修炼石台→闭关；山门→山海；丹炉→丹器；灵兽台→灵兽；藏物处→行囊。宗门从命册/更多入口进入，也可使用一个真实山门入口，但不因此新增系统。

热点外观：建筑/器物本体承担识别，旁边用短题签；普通状态不套大圆按钮。禁用或剧情占用时标明原因；警示点仅在真实可处理状态出现。

顶部常驻紧凑信息：境界、修为、年龄/寿元、元气、盘缠/行粮；次要量进入详情。低资源和伤势必须能发现。保留菜单与音景入口，不能为了干净把存档藏没。

底部情境条：显示当前目标与一个主要动作。可破境时明确显示破境；遇强制剧情时进入事件窗并暂停场景动作，不继续显示“清修无事”。闭关的收益和耗年必须可见，尤其临近寿尽。

基准 390×844：顶部信息约 64–88 px，底栏约 60–68 px 加底部安全区；主要动作位于底栏上方。中部至少约半屏留给可辨认的场景，不做空白海报。320×568 使用短屏构图，隐藏装饰，不隐藏必要操作或把字号缩小。

### 4.2 人物：CharNewWnd → CharacterWindow

首屏直接呈现境界、战力、道身、已穿戴器物、根骨/神识/悟性/气运。不能再用四个功能入口代替装备展示。

道身采用独立透明立绘/墨绘剪影，衣袍、站姿、轮廓必须完整，不使用 CSS 椭圆加梯形，不把洞府整张图当人物背景。沿用此前“无明确面貌”约束，不强行指定用户未选择的脸或性别。

接近参考的排版：道身偏左中，右侧两列小装备格；下部是属性条与功法/命册切换。不是四个等距菜单围着几何小人。

只展示现有四槽：weapon 兵器、artifact 法宝、robe 法衣、accessory 佩饰。调用 FSEquipment.equipped 与 data 取真实值。空槽显示空槽与可装备入口；未鉴定物品不得泄露真实名称与效果；“更好”只能基于可解释规则，不伪造比较分数。

点击槽位→当前物品与候选装备详情→沿用 equipment-equip / equipment-unequip 等真实动作。灵兽、宗门等作为次级页签/入口，不占据装备槽位置。高境界不自动增加虚构槽位。

### 4.3 行囊：BaggageWnd → BaggageWindow

首屏必须出现已有物品，不再有大号“囊”字法阵。灰白纸底，顶部容量与分类，中部紧凑物品行，底部选择详情或操作区。

候选分类：全部、装备、丹药、材料、补给；每一类只聚合现有数据。装备容量 12 只代表装备 inventory，不把材料和行粮计入这个容量。

每行采用 ItemCell：图标、品质细框、名称、数量/阶段、已穿戴/未鉴定状态。移动端行高目标 60–76 px，触控区至少 44×44 CSS px。不是把 12 件物品扩成 12 张长卡片。

“全部”使用带来源类型的 view model：装备 uid、丹药实例、材料 id、旅途补给。聚合只读，不能为统一界面重写存档结构。

点击物品出现底部详情：信息、真实消耗、可用动作。鉴定、穿戴、温养、归炉继续使用原 reducer；危险操作保留明确确认。选中项消失或归炉后清理 selection，不能点击旧 uid。

### 4.4 山海：WorldWnd → WorldMapWindow

保留现有六地十八路线及进度。地图与节点处于同一坐标系；滚动/拖动地图时地标和点击区域一起变换，不能背景 cover 裁切而按钮独立按百分比放置。

节点使用桥、山门、林地、城集等符号及题签，选中仅局部加印记。未解锁显示境界要求，不隐藏所有地理联系，不伪造行进道路。

选择地点后打开固定区域的情报/行前准备抽屉：路线目标、风险、工具、耗年、盘缠、行粮、伤势。去掉地图之外重复的六个大入口。出发后保留现有三段遭遇，不以镜头动画推进结算。

### 4.5 丹器：ForgeWnd → CraftWindow

原作结构中 oven / tripod / flame / smoke 与 cost_panel / probability / product / result 并存。本项目采用器炉中心舞台、材料槽、方子页签、成本与结果区，而不是纯背景。

丹药与兵器分两个页签，对应已有 crafting 数据。只展示已有算法能提供的信息，不虚构原作成功率、排队或自动生产。操作→引擎结算→炉火与结果表现；同一结果刷新不再领奖。

首次只做炼制窗口；HerbalGardenWnd 用作分层环境的参考，不添加一座不能工作的药园。

### 4.6 突破：TupoWnd / JinxianWnd → BreakthroughWindow

单独背景、角色、遮罩、阶段特效、境界文字、结果面板。显示优先级高于 HUD 与其它窗口。

候选节奏：0–250 ms 收束界面；250–900 ms 灵气聚拢；900–1500 ms 境界题字；1500–2200 ms 展示真实结果。避免高频闪白、全屏持续晃动、大块模糊遮住信息。

可跳过，跳过只结束表现；reduced-motion 下直接显示静态结果，不把整层隐藏导致玩家看不到破境结论。动画失败、切页、后台恢复不得再次触发 transition。完整标题和结果使用 HTML，不把动态文字烘焙进图。

### 4.7 HUD 与通用窗口

保留四个一级功能：洞府（内部 practice）、山海（atlas）、行囊（inventory）、人物（character）。原作有六个入口，不代表我们必须新增两个没有必要的系统。现有顺序先不变，避免同时修改操作记忆。

底栏采用统一绘制的小型图标、短名称、局部墨印选中态。视觉资源共用图集；非所有按钮都套一种圆章。红点只用于真实未处理状态，不能装饰性常亮。

设置/导入导出/音景在所有可导航阶段有可见入口；结束、创建角色、仙界和创世阶段分别声明菜单能力，不能仅依赖隐藏的 topbar。

通用 DialogFrame：标题区、内容 ScrollArea、底部操作条；边角保持比例，内容可增长。物品详情、日志、设置共用框架，不共用全部内部排版。

## 5. 美术制作合同

详细预算与状态见 `UI_V3_ASSET_MANIFEST.json`。所有新资源当前均为 planned，不是已生成文件。

必须先完成三张同尺寸设计稿：洞府、人物、行囊，使用固定示例状态。用户认可视觉方向后，才批量绘制其余窗口和状态。

### 固定示例状态

洞府稿可用“凡人、修为 0/100、盘缠 24、行粮 9/12”等样例数值，但标明为视觉样例，不作为存档。人物稿允许示意四件已有装备；最终运行必须取真实存档。行囊稿优先使用现有名称如玄铁长剑、照灵镜、青麻道衣、温玉戒，不发明新规则。

### 生产要求

- 背景必须按竖屏构图绘制；明确 HUD 保留区、建筑锚点、镜头裁切安全区，不能沿用横图生硬 cover。
- 建筑和人物独立透明图；前景云雾与枝叶有单独 alpha；底板、选中态、锁定态、图标有可重用资源。
- 美术图不带按钮文字、资源数值、光标或设备外壳；标签由代码绘制。
- 命名包含角色与层次；manifest 记录尺寸、锚点、透明区、来源、许可状态、hash、生成/人工修订记录。
- 角色可无面貌但不能无造型；“黑色剪影”不是可以使用粗糙几何占位的理由。
- 未完成的正式资产在开发预览中标记，不冒充发布完成。异常加载保留可操作的语义界面。
- 原作资源仅留在研究目录。本项目公开发布仅包含自己有权使用的代码、美术及资源；原作字体不复制、不打包、不分发。

## 6. 按参考构建，而不是复制不可运行的源码

### 6.1 映射关系

| APK 中观察到的对象 | V3 等价实现 | 边界 |
|---|---|---|
| Window Prefab | 独立窗口模板 + layout 配置 | 不是一个通用大卡片组件 |
| RectTransform | 受约束的锚点布局计算 | 保留父子结构、pivot、坐标轴差异 |
| Image / Sprite / SpriteAtlas | SpriteView + 自有 atlas manifest | 需要尺寸、切片与图标映射 |
| ScrollView / Viewport / Mask | 局部 ScrollArea / ClipViewport | 不让全页与弹窗出现多重无意滚动 |
| redpoint / unlock / select | 状态子节点与选择器 | 状态来自自己的引擎 |
| Lua 窗口资源 | 自己编写的 WindowController / Binder | Lua 负载未恢复，不能声称复用函数 |
| ParticleSystem / AnimationClip | 有预算的 CSS/WAAPI/Canvas 表现 | 不改变引擎规则与 RNG |

    rect-layout.js         锚点/透视无关的 UI 矩形计算
    asset-resolver.js      自有资源 id → URL、图集矩形、边框
    view-binder.js         白名单 selector → 文本/状态/进度
    fx-controller.js       表现时序与取消；不提交游戏动作

    baggage.window.js
    world-map.window.js
    craft.window.js
    breakthrough.window.js

### 6.3 运行时层级

```text
GameShell
  BackgroundRoot
  WindowRoot
    SceneArtwork / SubjectLayer
    ContentViewport
    SceneHotspots
  HUDRoot
    StatusBar / BottomNavigation / Menu
  ContextPanelRoot
  ModalRoot
  FullscreenEventRoot
  ToastRoot
```

常驻 shell 不因一次数值变化被整段 innerHTML 替换。窗口切换才挂载窗口；普通操作仅更新受影响文字、物品和状态。切换时保存本窗口滚动位置/选中项；过期选择必须校验。

统一层级 token 由 shell 管理；不得随意用 99999 压盖。装饰层 pointer-events:none，交互按钮保持语义、键盘焦点和 aria 状态。

### 6.4 动作与数据流

```text
用户点击
 → 控件发出语义 intent
 → GameAdapter 区分只读 UI 动作与游戏动作
 → 游戏动作携当前 revision，调用现有 E.transition 一次
 → 现有 persist 保存 run/meta
 → view model 重新计算
 → Binder 更新窗口
 → Presentation / Audio 读取前后态播放反馈
```

纯导航、打开详情、缩放地图、切页签不得改变随机数、奖励或游戏 revision。现有 carry-trace、教程设置、导入、新局等本来会改变数据的 UI 操作，必须单独列为数据操作，不能一概当成只读。

不要复制一份 engine 来适配新 UI。建立受控 adapter 后逐窗替换旧 renderer；保留旧 renderer 开关至回归结束。不可从另一个窗口越过强制剧情或途中限制。

### 6.5 RectTransform 转换要点

Unity 官方文档定义 anchor 为父矩形内比例，pivot 为自身比例；sizeDelta 与拉伸范围一起决定尺寸。导出字段 `size` 的语义必须经提取脚本/对象数据核对，不能直接视为屏幕像素宽高。

对未旋转、未缩放、未被 LayoutGroup 或动画改写的矩形，约定 `d` 为已经核实的 sizeDelta，父容器尺寸 W,H：

```text
width  = W * (anchorMax.x - anchorMin.x) + d.x
height = H * (anchorMax.y - anchorMin.y) + d.y
pivotX = W * lerp(anchorMin.x, anchorMax.x, pivot.x) + anchoredPosition.x
pivotY = H * lerp(anchorMin.y, anchorMax.y, pivot.y) + anchoredPosition.y
left   = pivotX - pivot.x * width
top    = H - pivotY - (1 - pivot.y) * height
```

这是对 Unity 底部向上坐标到 Web 顶部向下坐标的转换。父子矩形递归计算；旋转、scale、LayoutGroup、CanvasScaler、动画、代码驱动尺寸必须另处理并标记，不能盲目套公式。

例：假定父画布 800×1732，已读 HUD bar 的 sizeDelta=(0,130)、position=(0,65)、底部 stretch 和中心 pivot，计算矩形应为 left=0、top=1602、width=800、height=130。800×1732 是此例的输入，不是已证实全游戏唯一 CanvasScaler 分辨率。

Unity pathID 可能超出 JavaScript 安全整数；原始导出应使用 Python 整数解析并以字符串保存 ID，不能经过 JS Number 截断后再用于查依赖。

### 6.6 两套坐标与多视口

ArtSpace 负责统一比例的背景、建筑、角色、地图与对应热点；UIScreen 负责安全区内的 HUD、固定内容面板与底栏。ArtSpace cover 时必须把热点经过同一 scale/offset，不只缩背景。

设计母版建议宽 800，高 1600–1732；这是项目设计范围，不是硬拷贝某张纹理尺寸。高度差交给明确的长屏/短屏构图。

控制大小不盲目随画面缩小：小装备图标可以 32–40 px，实际点击范围仍至少 44×44 CSS px；标签下限 12 px。顶部刘海、底部手势区单独留白，不从按钮区域扣掉。

桌面保持居中的竖屏游戏区（候选 480–560 CSS px），两侧可用无交互的低对比背景，不再为填满宽屏添加日报侧栏或把洞府拉成横屏网页。最终宽度由 768/1280 验收稿确定。

### 6.7 样式迁移

先用 `.ui-v3-root` 隔离。旧页面仍使用旧样式；已迁移窗口不得继续被旧 `.game-shell`、全局 button 或 `.scene-ui.css` 的规则控制。

新窗口有独立样式，不向 scene-ui.css 再添加第 N 轮覆盖。移除旧文件前追踪首页、选天命、仙界、创世和弹窗依赖；不能直接删旧样式导致未迁移章节无样式。

原作图片的九宫格/切边需要实际 Sprite border 数据才可称为复现。本项目可为自有面板定义 border-image 九切参数，但不能把该参数描述成已提取的原作值。

## 7. 资源与性能预算

目标：ZIP <3,000,000 bytes，硬上限仍为 10,000,000 bytes；两者都要用构建结果验证，不能只加总美术文件估计。

新美术计划预算 2,350,000 bytes，预留 450,000 bytes 给压缩后代码/配置与容器开销、200,000 bytes 余量。此预算要求替代已失效的旧图，不能把两套全部带入生产包。若新图质量与预算冲突，先优化资源复用与画面尺寸，不先压小字号。

初期生产无新增字体和外部音频，沿用系统字与 WebAudio。两个环境循环已足够，不为每个按钮加粒子；隐藏页面停止动画，reduced-motion 静态，失败保留语义控件。

每个场景限制同时解码的高分辨率图层；透明留白裁切并记录偏移，避免大张透明 WebP 长期占内存。包大小不等于解码内存；后者须另测。

## 8. 验收不能再以“测试全绿”代替画面判断

G3：接现有引擎完成真实动作与存档回归；纯导航不改 run，所有游戏动作携 revision。

G4：320×568、360×800、390×844、430×932、768×1024、1280×800，三个主窗口和关键状态逐张视觉查看。检查按钮实际命中、建筑热点漂移、重叠、HUD 可读性、长名字、满背包、空槽、负伤、临界寿元和弹窗返回。不能只保存截图不打开看。
